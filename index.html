🤖 Connecting UI to AI Agents

Understanding AG-UI, A2UI, and MCP Apps Protocols

The Evolution of Agent-UI Communication

🧠 Agent ↔️ 🖥️ Interface

🎯 The Core Problem

Traditional AI agents respond with plain text

The challenge: When AI agents interact with users, they typically return only text responses. This creates several limitations:

  • ❌ Limited Expressiveness: Complex data like charts, forms, and interactive elements cannot be represented effectively as text
  • ❌ Poor User Experience: Users must parse long text responses instead of interacting with intuitive UI
  • ❌ No Real-Time Interaction: Agents can't create dynamic, interactive interfaces that respond to user actions
  • ❌ Lack of Standardization: Each agent framework implements UI generation differently, preventing interoperability

💡 What we need instead:

A standardized protocol that allows AI agents to:

  • ✅ Generate rich, interactive user interfaces
  • ✅ Stream UI updates in real-time as the agent processes information
  • ✅ Maintain bidirectional communication (agent ↔️ UI)
  • ✅ Work across different platforms and frameworks
  • ✅ Provide security and sandboxing for untrusted content

🌟 Solution Landscape: Three Approaches

Three major protocols have emerged to solve the agent-to-UI communication challenge, each with different trade-offs:

AG-UI - Controlled Generative UI
High Control | Pre-built Components | Type-Safe
↕️
A2UI - Declarative Generative UI
Balanced Control | JSON-based | Streaming
↕️
MCP Apps - Open-ended Generative UI
High Freedom | Full HTML/JS | Sandboxed

The spectrum: From most controlled (AG-UI) to most flexible (MCP Apps), these protocols offer different balances between developer control and agent freedom.

1️⃣ AG-UI (Agent-User Interaction Protocol)

📋 What is AG-UI?

AG-UI is a controlled generative UI protocol where developers pre-build UI components, and the AI agent selects which component to render and provides the data. Uniquely supports both server-side data fetching AND client-side UI state manipulation.

Type-Safe Pre-built Components Bidirectional Client-Side State Framework Agnostic

🔧 Two Types of Tools

📊 Server-Side Data Tools

Fetch external data and render pre-built React components:

// Define a tool that fetches data and renders a component
useFrontendTool({
  name: "get_weather",
  description: "Display weather information",
  parameters: z.object({ location: z.string() }),
  render: ({ status, result }) => {
    if (status === "executing") return ;
    return ;
  }
});

User: "Show me the weather in San Francisco"

→ Agent calls get_weather({ location: "San Francisco" })
→ UI renders <WeatherCard> with live data

🎮 Client-Side UI Tools (Instant Updates!)

Manipulate local React state directly — no server round-trip:

// 1. Define UI state
const [uiState, setUiState] = useState({
  sidebarOpen: true, theme: 'light', counter: 0
});

// 2. Let agent READ the state
useCopilotReadable({ description: 'Current UI state', value: uiState });

// 3. Let agent MODIFY the state
useCopilotAction({
  name: "toggle_sidebar",
  handler: async ({ open }) => {
    setUiState(prev => ({ ...prev, sidebarOpen: open }));
    return `Sidebar ${open ? 'opened' : 'closed'}`;
  }
});

User: "Close the sidebar"

→ Agent calls toggle_sidebar({ open: false })
→ React setState fires → UI updates in ~10ms ⚡

🎯 Client-Side Tool Examples

  • Sidebar Control: "Close the sidebar" → Instant toggle
  • Theme Switcher: "Change to dark mode" → Immediate theme change
  • Counter: "Increment counter" → Direct state update
  • Notifications: "Add notification: Meeting at 3pm" → Instant display
  • Navigation: "Switch to settings panel" → Immediate panel change
  • Context-Aware: "If counter > 10, reset it" → Agent reads & acts on state

✅ Advantages

  • Full Control: Developers own layout, styling, and UX
  • Type Safety: Compile-time validation of data structures
  • Instant Updates: Client-side tools execute in ~10-50ms
  • Bidirectional State: Agent can read AND modify UI state
  • Offline Capable: Client-side tools work without network
  • Consistent Design: All UI follows your design system
  • Security: Only predefined components can render
  • Performance: Optimized React components, no parsing overhead

⚠️ Limitations

  • Limited Flexibility: Agent can only use pre-built components
  • Upfront Work: Requires building components before agent can use them
  • Scalability: Need new components for new use cases
  • Not Truly Generative: Agent chooses, doesn't create UI structure

⚡ AG-UI's Killer Feature

Direct client-side state manipulation is AG-UI's unique advantage:

  • 🚀 A2UI: Must regenerate JSON and stream updates (slower)
  • 🚀 MCP Apps: Requires postMessage through iframe (complex)
  • ⚡ AG-UI: Direct React setState calls (instant!)

Result: Native app-like responsiveness in AI-controlled interfaces

🎯 Best Use Cases

  • Enterprise Applications: Where consistency and brand compliance are critical
  • Regulated Industries: Healthcare, finance where UI must be audited
  • Interactive Dashboards: Real-time UI updates without server latency
  • Offline-First Apps: Client-side tools work without network
  • Known Workflows: Limited set of well-defined operations
  • High Security Requirements: No risk of arbitrary code execution

🎮 AG-UI: Client-Side State Control

AG-UI's Killer Feature

Direct manipulation of client-side React state enables instant UI updates without server round-trips. This makes AG-UI perfect for responsive, offline-capable agent UIs.

📊 Server-Side Tools

For: External data fetching

  • Weather data
  • User profiles
  • Charts from APIs
  • Database queries
Latency: 500ms-2s

🎮 Client-Side Tools

For: UI state manipulation

  • Toggle sidebar

💬 Real-World Examples

Example 1: Simple Toggle

User: "Close the sidebar"

1. Agent calls toggle_sidebar({ open: false })

2. Tool executes: setUiState(prev => ({ ...prev, sidebarOpen: false }))

3. React re-renders → Sidebar disappears instantly ⚡

✓ No server call needed!

Example 2: Context-Aware Action

User: "If the counter is above 10, reset it"

1. Agent reads state via useCopilotReadable → counter = 15

2. Agent checks condition: 15 > 10 ✓

3. Agent calls update_counter({ action: 'set', value: 0 })

4. Counter resets instantly

✓ Agent makes intelligent decisions based on current state!

Example 3: Multiple Actions

User: "Close sidebar, change to dark theme, and increment counter"

1. Agent calls toggle_sidebar({ open: false })

2. Agent calls change_theme({ theme: 'dark' })

3. Agent calls update_counter({ action: 'increment' })

4. All three execute in sequence, ~50ms total

✓ Chained actions feel instant!

2️⃣ A2UI (Agent-to-UI Protocol)

📋 What is A2UI?

A2UI is a declarative generative UI protocol developed by Google. The agent returns structured JSON that describes UI components, and the frontend renders them based on the specification.

Google-backed JSONL Streaming Platform Agnostic Declarative Open Standard

🔧 How It Works

Agent streams JSONL messages describing UI structure. Renderer interprets and displays:

// Message 1: Define components
{"surfaceUpdate": {
  "surfaceId": "contact-form",
  "components": [
    {"id": "root",  "component": {"Column": {"children": ["title","name","email","submit"]}}},
    {"id": "title", "component": {"Text": {"text": "Contact Us", "usageHint": "h2"}}},
    {"id": "name",  "component": {"TextField": {"label": "Name", "placeholder": "Your name"}}},
    {"id": "email", "component": {"TextField": {"label": "Email"}}},
    {"id": "submit","component": {"Button": {"label": "Send"}}}
  ]
}}

// Message 2: Bind data model
{"dataModelUpdate": {"surfaceId": "contact-form", "path": "/", "contents": {}}}

// Message 3: Signal to render
{"beginRendering": {"surfaceId": "contact-form", "root": "root"}}

Result: Renderer receives these 3 messages and displays a fully interactive contact form with text inputs and a submit button — all from JSON, no HTML.

✅ Advantages

  • True Generative UI: Agent creates UI structure on-the-fly
  • Streaming Support: Progressive rendering as data arrives
  • Platform Agnostic: Works on iOS, Android, Web, HarmonyOS
  • Structured: Well-defined component vocabulary
  • Balanced: Agent has freedom within component constraints
  • Google Backing: Strong ecosystem support

⚠️ Limitations

  • Limited Components: Only ~22 built-in components
  • Learning Curve: Agents must learn JSONL format
  • Renderer Required: Need platform-specific implementation
  • Less Control: Styling and layout determined by renderer
  • Complex State: Managing dataModelUpdate can be intricate

📦 A2UI Component Set

A2UI includes ~22 primitive components:

📝 Text
🔘 Button
📊 Column
↔️ Row
🖼️ Image

✅ Checkbox

🎯 Best Use Cases

  • Cross-Platform Apps: Need same UI on iOS, Android, Web
  • Dynamic Dashboards: Data visualization that changes based on queries
  • Form Generation: Creating forms based on agent understanding
  • Progressive Enhancement: Stream UI as agent gathers information
  • Moderate Flexibility: Balance between control and freedom

🔄 A2UI Bidirectional Communication

A2UI has built-in bidirectional support through its data model and action system:

  • Agent → UI: updateComponents + updateDataModel messages stream UI and state to the renderer
  • UI → Agent: Components declare actions with events. When a user clicks a button or submits a form, the renderer fires the event with context containing bound data model values back to the agent
  • Data Binding: Components bind to paths in the data model (e.g., /form/email). User input updates the model locally; on submit, the full state is sent back
// Button with action — sends data back to agent on click
{
  "id": "submit-btn",
  "component": "Button",
  "action": {
    "event": {
      "name": "form_submit",
      "context": {
        "email": {"path": "/form/email"},
        "name": {"path": "/form/name"}
      }
    }
  }
}

vs MCP Apps: A2UI's bidirectional flow is part of the protocol spec and works today. MCP Apps relies on postMessage which most clients don't yet relay back to the agent.

3️⃣ MCP Apps (Model Context Protocol Apps)

📋 What are MCP Apps?

MCP Apps are open-ended generative UI applications that render complete interactive HTML interfaces inside MCP-enabled hosts (like Claude Desktop, VS Code). The agent can return full HTML/CSS/JS applications.

Full HTML/CSS/JS Sandboxed iframes Claude Support VS Code Support Maximum Freedom

🔧 How It Works

MCP server exposes tools that return full interactive web apps:

# 1. MCP Server declares a tool with a UI resource
@server.tool()
def create_chart(data: list, chart_type: str):
    """Create an interactive chart visualization"""
    return ToolResult(
        content="Chart created successfully",
        ui=UIResource(uri="ui://chart-view")  # ← full HTML app
    )

# 2. Host fetches the UI resource → gets complete HTML/JS
# 3. Renders in sandboxed iframe within the chat
# 4. App can communicate back via postMessage:
# app.send("tools/call", { tool: "update_data", params: {...} })

Result: A fully interactive D3.js chart appears inline in Claude Desktop or VS Code — with zoom, hover tooltips, and the ability to request new data from the agent.

✅ Advantages

  • Maximum Flexibility: Full web platform available
  • Rich Interactivity: 3D graphics, video, complex animations
  • Existing Ecosystems: Use Three.js, D3, any JS library
  • No Limits: Any UI that works in a browser
  • Context Preservation: UI stays in conversation
  • Bidirectional (spec): Spec defines postMessage for app↔host communication

⚠️ Limitations

  • Security Risk: Must sandbox untrusted HTML/JS
  • Inconsistent Styling: Each app has its own design
  • Performance: Heavy apps can slow down the host
  • Complexity: Requires building full web apps
  • Limited Portability: Web-only, doesn't work on native mobile
  • Client Support: Requires MCP Apps-capable host
  • Bidirectional Gap: Most clients (VS Code, Claude Desktop) don't yet relay user input from the iframe back to the agent conversation

⚠️ Bidirectional Communication: Current Reality

The MCP Apps spec defines postMessage for app↔host communication, but in practice:

  • Agent → UI: ✅ Works — agent calls tool, server returns HTML, client renders it
  • UI → Agent: ❌ Not yet supported — user interactions in the iframe (form submissions, button clicks) cannot feed back into the agent conversation in most clients

Result: MCP Apps are currently best for displaying rich interactive content, not for collecting user input that the agent can act on. The user must communicate choices back via text.

🎨 Real-World Example: Excalidraw MCP App

Use case: AI-powered diagramming

  1. User: "Create a system architecture diagram for a microservices app"
  2. Agent calls create_view tool with Excalidraw JSON elements
  3. MCP server returns fully interactive Excalidraw canvas as HTML
  4. Renders in Claude Desktop as sandboxed iframe
  5. User can edit the diagram directly in the canvas
  6. User: "Add a database" → Agent calls tool again with updated elements → new iframe replaces the old one

⚠️ The Update & State Problem

How does the agent "update" the diagram? It doesn't push into the iframe — it calls the tool again, generating a completely new HTML page. The client replaces the old iframe with the new one.

What if the user edits the diagram in the UI? Those edits are invisible to the agent. They live only in the iframe's local JavaScript state. If the agent calls the tool again, user edits are lost (overwritten by the new render).

Workaround: The iframe app could persist state back to the MCP server via direct HTTP calls (e.g., fetch('/save')), so the server can merge user edits with agent updates on the next tool call. But this requires custom implementation — it's not part of the MCP Apps protocol.

🎯 Best Use Cases

  • Data Visualization: Complex charts, 3D models, interactive graphs
  • Document Viewers: PDFs, presentations, rich media
  • Creative Tools: Drawing, design, music composition
  • Specialized Applications: Code editors, calculators, game simulations
  • Third-party Integrations: Embed existing web apps

🔗 How They Relate: MCP & A2A

Understanding the Protocol Stack

AG-UI, A2UI, and MCP Apps don't exist in isolation. They're part of a larger ecosystem of agent protocols:

📚 Model Context Protocol (MCP)

MCP is the foundation - it's an open standard for connecting AI applications to external systems (data sources, tools, workflows).

What MCP Does:

  • 🔌 Tool Calling: Agents can invoke external functions/APIs
  • 📁 Resource Access: Connect to databases, file systems, APIs
  • 💬 Context Injection: Provide agents with relevant information
  • 🔄 Bidirectional Communication: Client ↔️ Server messaging

Key Insight: MCP Apps is an extension of MCP that adds UI rendering capabilities to the core protocol. While MCP handles data and tools, MCP Apps handles interactive interfaces.

🤝 Agent-to-Agent (A2A) Protocol

A2A is about agent communication - it's an open standard (from Google, now Linux Foundation) for agents to talk to other agents.

What A2A Does:

  • 🤖 Interoperability: Agents from different frameworks can collaborate
  • 🔀 Task Delegation: Agents can hand off subtasks to specialized agents
  • 🔐 Secure Communication: Agents don't need to share internal state
  • 🌐 Decentralized: No central authority required

Key Insight: A2A and MCP are complementary. MCP connects agents to tools/data, while A2A connects agents to other agents. Together they enable powerful multi-agent systems.

💡 Key Takeaway

These protocols form a composable ecosystem:

  • MCP = How agents access tools and data
  • A2A = How agents talk to each other
  • AG-UI / A2UI / MCP Apps = How agents present information to humans

You can mix and match these protocols based on your needs. An agent might use MCP for data access, A2A for delegation, and A2UI for UI rendering—all in the same application.

✨ Final Thoughts

The future of AI isn't just text responses—it's rich, interactive, agentic interfaces that adapt to user needs in real-time. Whether you choose the safety of AG-UI, the balance of A2UI, or the freedom of MCP Apps depends on your specific requirements.

The best applications will likely use all three: AG-UI for critical flows, A2UI for dynamic content, and MCP Apps for specialized rich experiences.
